# ROSIDE: ตรวจการสื่อสารและคิวงาน — 14 พฤศจิกายน 2026

ลดภาระได้ โดยจุดที่มีหลักฐานชัดที่สุดคือตัวอ่าน telemetry จาก PTY และการอ่านลำดับคิว MapSim จากไฟล์ซ้ำ การตรวจครั้งนี้อ่านโค้ดและทดสอบจำลองแยกจากบริการจริง ไม่ได้ส่งคำสั่งให้หุ่นเคลื่อนที่ ไม่ได้เปลี่ยนโค้ดที่ให้บริการ และไม่ได้ restart Server/Agent

ตัวอย่างการวัดโปรเซส ROSIDE นาน 2.5 วินาทีระหว่างตรวจ: CPU ประมาณ 0.4% ของหนึ่งคอร์ และ RSS ประมาณ 92.8 MiB ตัวอย่างสั้นนี้ยังใช้สรุปความจุผู้ใช้/หุ่นพร้อมกันไม่ได้

| สิ่งที่มีอยู่แล้ว | หลักฐาน |
|---|---|
| MapSim ทำงานหนักทีละงานและจำกัดคิวรอ 230 งาน | `mapsim-queue.js`, ใช้ `flock` และ ticket ในไฟล์ร่วมกันระหว่างโปรเซส |
| การสแกนความคืบหน้าหุ่นจำกัดพร้อมกัน 2 งานโดยปริยาย | `ROBOT_PROGRESS_CONCURRENCY` ใน `server.js` |
| Dashboard รวมคำขอที่กำลังทำงานและ cache สถานะหุ่นจริง 5 วินาที | `getDashboardRuntime()` |
| มีเพดานข้อมูลรอส่งบน WebSocket และขนาดเฟรม | Browser telemetry 4 MiB, Agent 8 MiB, ตัวอ่าน PTY 16 MiB |
| คำสั่งควบคุมมีการตรวจอายุ | Agent ออก command ticket ทุก 250 ms และปฏิเสธ ticket อายุเกิน 1.5 วินาที |

## 1. ควรแก้ก่อน: ตัวอ่าน PTY วนอ่านข้อความเดิมซ้ำ

`server.js: routeAgentPtyMessage()` ต่อข้อความใหม่เข้ากับข้อความค้าง แล้วเริ่มนับวงเล็บ JSON ใหม่ตั้งแต่ต้นทุกครั้ง เมื่อ JSON แผนที่ใหญ่ถูกแบ่งเป็นหลายชิ้น งานจึงเพิ่มใกล้เคียง O(n²) ตามจำนวนชิ้น แทนที่จะอ่านข้อมูลแต่ละตัวอักษรครั้งเดียว ทั้งการต่อ string และ `Buffer.byteLength()` ของข้อความสะสมยังทำงานซ้ำ

ทดสอบด้วยข้อมูลแผนที่สังเคราะห์ 360 × 360 ช่อง ขนาดเฟรม 388,956 bytes จำนวน 3 เฟรม ผ่านตัวอ่านปัจจุบันที่สกัดจาก `server.js` เทียบกับต้นแบบ incremental parser ที่ยังทำ JSON parse/serialize ตอนเฟรมสมบูรณ์เหมือนกัน:

| ขนาดชิ้นที่ส่ง | ชิ้น/เฟรม | ตัวอ่านเดิม รวม 3 เฟรม | ต้นแบบ รวม 3 เฟรม | อัตราเร็วโดยประมาณ |
|---|---:|---:|---:|---:|
| 1 KiB | 380 | 1,362 ms | 52 ms | 26 เท่า |
| 4 KiB | 95 | 395 ms | 28 ms | 14 เท่า |
| 16 KiB | 24 | 155 ms | 25 ms | 6 เท่า |

นี่เป็นผลเฉพาะตัวอ่านในงานจำลอง ไม่ใช่การลด CPU หรือเพิ่มความเร็วทั้ง ROSIDE ในอัตราเดียวกัน ต้นแบบมีไว้เปรียบเทียบ ยังไม่ได้แทนที่ตัวอ่านจริง ก่อนใช้งานต้องรักษาเพดาน 16 MiB และตรวจ escaped quotes, วงเล็บใน string, หลายเฟรมใน chunk เดียว, เฟรมขาดตอน, Unicode, การปิด PTY และการส่งสถานะสำคัญเมื่อ Browser ช้า

แนวทาง: เก็บ depth/string/escape และชิ้นข้อความต่อ PTY แล้วอ่านเฉพาะข้อความใหม่ รวม string เมื่อเฟรมจบ อีกส่วนที่ช่วยได้คือ batch output ฝั่ง `agent-runtime.js` ประมาณ 4 ms แบบมีเพดานขนาด โดยไม่ batch คำสั่งควบคุมขาเข้า ปัจจุบัน runtime ที่ใช้งานส่งทุก `terminal.onData()` ทันที ส่วน legacy fallback มี batching อยู่แล้ว

## 2. ควรแก้ก่อนรองรับคิวใหญ่: การถามลำดับคิวอ่านทุกไฟล์แบบ synchronous

`MapsimQueue.status()` → `MapsimJobStore.position()` → `waiting()` → `list()` อ่านไฟล์ทุกงานใหม่ และตรวจ owner PID ซ้ำทุกงาน การถามตำแหน่งเพียงหนึ่งงานจึงอ่านทั้งคิว รวมถึง `/proc` ของ owner ซ้ำ

ทดสอบด้วยไฟล์ ticket จำลองใน temporary directory ไม่ใช้คิวจริง:

- คิว 20 งาน: 40 file reads ต่อการถามลำดับหนึ่งครั้ง
- คิว 100 งาน: 200 file reads ต่อครั้ง
- คิว 230 งาน: 460 file reads ต่อครั้ง; ตัวอย่างแรกใช้ประมาณ 5.1 ms ต่อครั้ง

Browser รอคิว poll ทุก 2 วินาที หากมีผู้รอหลายคน การเรียก status จะอ่านชุดไฟล์เดียวกันซ้ำ และ synchronous I/O จะใช้เวลาใน event loop ที่รับคำสั่งอื่นด้วย ผลวัดที่ทำซ้ำได้อยู่ใน `performance-audit/queue-results-20261114.json`

แนวทาง: สร้าง snapshot ตำแหน่งของทุกงานครั้งเดียวต่อช่วงสั้น 250–500 ms, ตรวจ owner แต่ละ PID ครั้งเดียวต่อ snapshot และ invalidate เมื่อมีการเขียนงาน ต้องยังรักษา shared tickets, ตรวจโปรเซสที่ตาย และ `flock` ไว้ ไม่ควรแทนที่ด้วยคิวใน memory อย่างเดียวเพราะมีหลายโปรเซส

## 3. ลดงานซ้ำ: รวมคำขอตรวจสถานะ Mapping/Nav2 ต่อหุ่น

Dashboard มีการรวมคำขอและ cache แล้ว แต่ handler `/api/mapping/runtime` และ `/api/navigation/runtime` ยังรันคำสั่งตรวจ process/log/ROS graph สำหรับคำขอ status แต่ละครั้ง หน้าเว็บมีตัวกันคำขอซ้อนเฉพาะในแท็บ และหลายหน้าจะตรวจทุก 5 วินาทีเมื่อข้อมูล scan ไม่สด

แนวทาง: รวมคำขอ read-only ที่กำลังทำงานต่อ robot + workspace + action และ cache ผลสำเร็จสั้นประมาณ 1 วินาที ตรวจสิทธิ์และ control lease ก่อนเข้า cache และ invalidate ทันทีเมื่อ start/stop/reconnect ไม่ใช้ cache ร่วมกับคำสั่งเปลี่ยนสถานะ

## 4. ลดข้อความสถานะ Agent โดยคงอายุคำสั่งเดิม

`agent-runtime.js: pulse()` เรียก `announce()` ทุก 250 ms แล้วคำนวณ status ใหม่ต่อ link และอีกครั้งให้ `onStatus()` ในกรณี online + local หนึ่ง pulse ทำให้ enumerate network interfaces 6 ครั้ง การทดสอบบนเครื่องนี้ส่ง status รวม 1,286 bytes ต่อ pulse ของสอง links หรือประมาณ 5.1 KB/s โดยยังไม่รวม WebSocket/TCP overhead

แนวทางแรกที่เสี่ยงต่ำ: คำนวณ snapshot เพียงครั้งเดียวต่อ announce และ cache network-interface metadata ระยะสั้น ขั้นต่อไปแยกการส่ง command ticket ขนาดเล็กทุก 250 ms ออกจาก metadata เต็มที่ส่งเมื่อเปลี่ยน/เป็นระยะ ต้องปรับ Server ให้ไม่ล้าง metadata เมื่อรับ packet บางส่วน และทดสอบ freshness/mode switch เดิม ไม่ควรลดความถี่ ticket โดยตรงเพียงเพื่อลด traffic

## 5. จำกัดงาน Agent ตามประเภท ไม่ต่อคิวทุกคำสั่งรวมกัน

`agentReq()` ส่งคำขอทันทีและเก็บใน `pendingReqs` จนตอบกลับ/timeout ยังไม่มีเพดานรวมต่อ robot ส่วน `robotProgressQueue` จำกัดจำนวนงานที่ทำพร้อมกันแต่ไม่มีเพดานงานรอ ขณะมีหลายผู้ใช้ งาน exec/อ่านไฟล์อาจซ้อนกันได้มากกว่าคิวสแกนภารกิจที่มีอยู่

แนวทาง: เพิ่มเพดานและเวลารอสูงสุดสำหรับ background exec พร้อมความยุติธรรมต่อ robot และรวม read-only requests ที่เหมือนกัน แยก I/O ที่ต้องทำงานคู่กับ exec เช่นการเขียน sudo FIFO ออกจากคิว exec เพื่อไม่ให้ deadlock และรักษา CAS/ลำดับการเขียนไฟล์

คำสั่งหยุด การควบคุมมอเตอร์ และ PTY input ต้องผ่านได้โดยไม่รอคิวงานหนัก ไม่ replay คำสั่งเคลื่อนที่หลัง reconnect และไม่ retry คำสั่งเขียน/ติดตั้งอัตโนมัติเพียงเพราะ timeout

## 6. ลด hashing ซ้ำใน endpoint Agent release

`sourceDigest()` อ่าน 133 ไฟล์ รวมประมาณ 4.62 MB ในการตรวจครั้งนี้ ใช้ประมาณ 23–30 ms ต่อรอบ `ensureRelease()` ที่ไม่มีไฟล์เปลี่ยนใช้ประมาณ 29 ms มีทั้ง timer ทุก 30 วินาที และ endpoint release/status ที่เรียกตรวจซ้ำ

แนวทาง: ให้ public endpoint เสิร์ฟ manifest ที่ตรวจสอบแล้วจาก cache ส่วนการ rebuild/ตรวจ checksum ทำเบื้องหลังหรือเมื่อมีการ deploy เปลี่ยนไฟล์ และตรวจความสดอีกครั้งก่อนเริ่มติดตั้งจริง จุดนี้มีผลน้อยกว่า parser ภายใต้ telemetry หนัก แต่ช่วยลดงานซ้ำเมื่อมีหลาย Agent ตรวจอัปเดต

## การวัดผลก่อนและหลังที่ควรเพิ่ม

เก็บ event-loop lag p95/p99, telemetry bytes/sec และจำนวนเฟรมที่ข้ามเพราะ backpressure, จำนวน pending requests ต่อ robot, เวลารอ/เวลาทำงานคิว และจำนวน ROS probes ที่ถูกแชร์ ปัจจุบัน `/api/health` ตอบสถานะบริการ/เวอร์ชัน ยังไม่ให้ข้อมูลเหล่านี้

ลำดับลงมือที่แนะนำ: (1) incremental PTY parser (2) snapshot ตำแหน่งคิว (3) รวม runtime-status requests แล้ววัดซ้ำ (4) ลด metadata heartbeat และเพิ่มเพดาน Agent งานเบื้องหลัง

ทำซ้ำจากโฟลเดอร์โครงการ:

```sh
node performance-audit/communication-benchmark.js
node performance-audit/queue-benchmark.js
```

การทดสอบทั้งสองสร้างข้อมูลสังเคราะห์ ไม่เชื่อมต่อหุ่น ไม่เปิดพอร์ตควบคุม และไม่ใช่ load test ความจุระบบจริง

# ผลปรับปรุงหลังได้รับคำสั่งให้ดำเนินการ

ดำเนินการกับ Server และแพ็กเกจ Local/Agent แล้วดังนี้:

- ใช้ `PtyJsonStream` อ่านเฟรมต่อเนื่องโดยไม่สแกนข้อความเก่าซ้ำ รองรับ UTF-8 ที่ถูกแบ่งกลางตัวอักษร รักษาเพดาน 16 MiB และล้าง state เมื่อ PTY ปิด
- ใช้ snapshot ตำแหน่งคิว 250 ms พร้อมตรวจ directory timestamp ทุกครั้ง จึงเห็น atomic writes จากอีกโปรเซสได้ทันที ตรวจ owner แต่ละ PID ครั้งเดียวต่อ snapshot และไม่อนุญาตให้เริ่มงานจาก snapshot ที่ไฟล์เปลี่ยนระหว่างอ่าน
- รวมคำขอ read-only Mapping/Nav2 ที่กำลังทำงาน และเก็บผล 1 วินาที แยก robot/workspace/tool ตรวจสิทธิ์ก่อนใช้ cache และ invalidate เมื่อ start/stop/disconnect
- Batch เฉพาะ PTY output ฝั่ง Agent ไม่เกิน 4 ms หรือ 64 KiB พร้อม flush ก่อนแจ้งปิด terminal คำสั่งควบคุมขาเข้าไม่ผ่าน batch นี้
- ส่ง heartbeat แบบย่อเมื่อ metadata ไม่เปลี่ยน แต่ยังออก ticket ทุก 250 ms ส่งข้อมูลเต็มเมื่อเปลี่ยนหรือครบ 5 วินาที และคำนวณ network interfaces ผ่าน cache 1 วินาที คำขอ `agent_status` ยังได้ข้อมูลเต็ม
- จำกัดคำขอที่ยังไม่เสร็จ 1,024 ต่อ Server, 64 ต่อ robot และ exec 8 ต่อ robot โดยปริยาย งานล้นจะถูกปฏิเสธอย่างชัดเจน ไม่เก็บคำสั่งไว้ replay คำสั่งมอเตอร์/STOP/PTY ใช้เส้นทางเดิม และ `control_select`/`agent_status` ไม่ติดเพดานนี้ การเขียนไฟล์ไม่ได้ใช้ช่อง exec จึงยังเขียน sudo FIFO คู่กับ exec ได้
- จำกัดคิวตรวจความคืบหน้าที่รอไว้ 256 งาน
- รวม/cache การตรวจ release ใน endpoint 1 วินาที และบังคับตรวจใหม่ก่อนเริ่มอัปเดต Agent จริง การตรวจ checksum และ timer ตรวจ source เดิมยังอยู่

กำหนดเพดาน request ผ่าน `AGENT_MAX_PENDING`, `AGENT_MAX_PENDING_PER_ROBOT`, `AGENT_MAX_EXEC_PER_ROBOT` ได้ ค่าทั้งสามเป็นการจำกัดงานที่ยังไม่ตอบกลับ ไม่ใช่คิวคำสั่งควบคุมหุ่น

| การทดสอบจำลองแบบเดิม | ก่อน | หลัง |
|---|---:|---:|
| JSON แผนที่ 389 KB × 3 เฟรม, chunk 4 KiB | 395 ms | 37 ms |
| คิว 230 งาน, ถามตำแหน่ง 20 ครั้ง | 99.8 ms / 9,200 reads | 4.3 ms / 231 reads |
| heartbeat 20 รอบ รวม online + local | 25,720 bytes | 8,848 bytes |

ผลนี้เป็นการทดสอบเฉพาะส่วนแบบออฟไลน์ ไม่ใช่ตัวเลขลด CPU ทั้งระบบตามสัดส่วนเดียวกัน และไม่ใช่การยืนยันจำนวนหุ่นพร้อมกันสูงสุด ผลวัดหลังแก้อยู่ใน `performance-audit/*-after.json`

ทดสอบ regression และส่วนสื่อสาร/คิวรวม 131 รายการ: ผ่าน 129, ข้าม 2, ไม่ผ่าน 0 โดยปรับ assertion เก่าที่อ้าง cache version และจำนวนปุ่มจากหน้าตารุ่นก่อนให้ตรงกับฟีเจอร์ที่เพิ่มไว้แล้ว พร้อมแทนบาง regex ด้วยการตรวจพฤติกรรมการส่งคำสั่งจริง

ส่วนที่เปลี่ยนใน Agent จะเริ่มใช้บนหุ่นเมื่ออัปเดต Agent ส่วนการปรับ parser/cache/คิวฝั่ง Online เริ่มใช้หลัง reload บริการ
